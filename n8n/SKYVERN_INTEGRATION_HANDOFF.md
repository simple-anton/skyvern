# Хендовер: оркестрация Skyvern-ботов (логин + парсер)

Документ описывает **логику**, а не n8n — чтобы её можно было повторить в любом другом
инструменте (Temporal, Airflow, обычный cron-скрипт на Python/Node, Zapier/Make и т.д.).
n8n-специфика (`$('Node').first()`, `resumeUrl`, ноды) упоминается только там, где это
нужно, чтобы объяснить, какую ошибку не стоит повторять.

Ссылки вида `service.py:2011` — на файлы этого репозитория (`skyvern/forge/sdk/...`),
чтобы можно было перепроверить поведение в первоисточнике, а не поверить мне на слово.

---

## 1. Что это вообще делает

Есть N поставщиков (TPP — third-party provider), у каждого свой личный кабинет со своим
логином. Нужно регулярно открывать в этом кабинете конкретный booking_id и вытаскивать из
него структурированные данные (даты, гостей, номер брони и т.д.).

Для этого на **каждого поставщика** в Skyvern заведено два независимых AI-агента (workflow):

- **Login-бот** — умеет только логиниться в личный кабинет и сохранять браузерную сессию.
- **Parser-бот** — умеет только найти конкретный `booking_id` и извлечь данные. Сам логин
  не делает — ожидает, что откроется уже в авторизованном браузере.

Оркестратор (сейчас — n8n-воркфлоу) держит три таблицы (Google Sheets, но с тем же успехом
это три таблицы в Postgres) и решает: для какого booking_id какого бота когда запускать,
передавать ли ему сохранённую сессию, и что делать, если сессия протухла.

Ключевая экономическая идея: **логиниться дорого** (это отдельный LLM-агентный прогон,
который стоит денег и времени), **парсить один booking_id дёшево**, а один логин
действителен для *множества* последующих парсингов, пока сессия жива. Вся сложность
оркестратора — в том, чтобы логиниться *ровно тогда, когда это необходимо*, и ни разу
лишний раз.

## 2. Модель данных (3 таблицы)

### 2.1 `Suppliers` — один поставщик = одна строка

| колонка | пример | назначение |
|---|---|---|
| `TPP` | `DDA` | человекочитаемый код поставщика |
| `website_url` | `https://portal.dida.com/login` | URL, с которого стартует и логин-бот, и (обычно) парсер-бот |
| `login_workflow_id` | `wpid_561706314685463142` | id Skyvern-воркфлоу логин-бота (общий на всех поставщиков в этом случае, но может быть свой на каждого) |
| `parser_workflow_id` | `wpid_561235100938517884` | id Skyvern-воркфлоу парсер-бота **этого конкретного поставщика** (у каждого свой, т.к. вёрстка кабинета разная) |

### 2.2 `Feeds` — один фид = одна связка «сайт + учётка»

Одна строка = один логин в один личный кабинет. У поставщика может быть несколько фидов
(например, разные аккаунты/договоры на одном сайте).

| колонка | кто пишет | назначение |
|---|---|---|
| `feed_id` | человек | уникальный ключ фида, например `DDA.B2C_CUG_DIRECT` |
| `website_url` | человек | должен совпадать с `website_url` в Suppliers (связка) |
| `bitwarden_item_id_input` | человек | UUID записи в Bitwarden с логином/паролем от этого кабинета |
| `agent_code` | человек | опциональный доп. код, который просит логин-форма (не у всех порталов) |
| `browser_profile_id` | **система** | id сохранённого браузерного профиля (`bp_...`). **Пусто для новых фидов** — заполняется сама после первого логина |
| `last_login_status` / `last_login_at` / `last_login_run_url` | система | диагностика последнего логин-прогона |
| `use_browser_session` | человек | `TRUE`/`FALSE`. См. §7 — режим «живая сессия» вместо профиля, для порталов, которые не принимают сохранённые профили |
| `browser_session_id` | система | id живой браузерной сессии (`pbs_...`), только для `use_browser_session=TRUE` |

**Важно**: `browser_profile_id` и `browser_session_id` — это *кеш*, не источник истины.
Источник истины — Skyvern (он владеет профилями/сессиями); таблица просто запоминает,
какой из них последний раз работал для этого фида, чтобы не логиниться заново.

### 2.3 `Jobs` — один booking_id = одна строка (очередь задач)

| колонка | кто пишет | назначение |
|---|---|---|
| `feed_id` | человек | какой фид парсить (внешний ключ на Feeds) |
| `booking_id` | человек | что искать в кабинете |
| `status` | система | `""` (пусто, новая) → `processing` → `completed` \| `failed` \| `timeout` \| `error` |
| `workflow_run_id` | система | id последнего парсер-прогона Skyvern (`wr_...`) |
| `recovered_via_login` | система | человекочитаемая диагностика: понадобился ли повторный логин и почему |
| `last_run_at` | система | таймстамп последней попытки |
| `extracted_data` | система | сырой JSON, который вернул парсер |
| `parser_run_url` / `login_run_url` | система | прямые ссылки на прогоны в Skyvern UI, для разбора инцидентов |
| `hotelName`, `address`, `checkinDate`, ..., `adultCount`, `hcn` | система | те же данные из `extracted_data`, разложенные по колонкам — для удобства (сортировка/фильтрация/экспорт), сам JSON не заменяется |

**Связки**: `Jobs.feed_id → Feeds.feed_id → Feeds.website_url → Suppliers.website_url`.
Чтобы добавить поставщика/фид/задачу — просто новая строка в нужной таблице, логику
оркестратора трогать не нужно.

**Повторный запуск идемпотентен**: оркестратор на старте читает Jobs и берёт **все строки,
где `status != completed`** (пустые, `failed`, `timeout`, `error`, зависшие `processing`).
Значит краш посреди работы не теряет задачи — следующий запуск сам их подхватит.

## 3. Ключевые понятия Skyvern, без которых логика непонятна

### 3.1 Workflow vs Workflow Run

**Workflow** — это определение агента (промпт, схема извлечения данных, настройки). У него
постоянный id вида `wpid_...`. Создаётся один раз в Skyvern UI/API, дальше только
**запускается** много раз.

**Workflow Run** — один конкретный запуск этого агента с конкретными параметрами. У него id
вида `wr_...`. Именно с run'ами работает оркестратор: диспатчит новый run, потом опрашивает
его статус.

### 3.2 Browser Profile — сохранённая браузерная сессия «на паузе»

Профиль (`bp_...`) — это снятый на диск слепок состояния браузера (куки, localStorage,
сессионные токены) **после того, как браузер закрылся**. Следующий запуск может попросить
Skyvern стартовать новый браузер, предзаполненный этим профилем — получится «как будто я
никогда не выходил из аккаунта».

Важная деталь именно про наш кейс — **managed-профиль с ключом**. Если у воркфлоу включено:
- `persist_browser_session: true` (тумблер **Save & Reuse Session** в UI)
- `browser_profile_key: "{{website_url}}-{{bitwarden_item_id_input}}"` (шаблон, Skyvern
  подставляет туда реальные значения параметров текущего запуска и берёт хеш)

...то при **каждом** запуске этого воркфлоу без явно переданного `browser_profile_id`
Skyvern делает **get-or-create**: если профиль с таким ключом уже существует — использует
его; если нет — создаёт новый (`_ensure_managed_browser_profile`,
`skyvern/forge/sdk/workflow/service.py:2269`). При успешном завершении run'а Skyvern
**дозаписывает** в этот профиль новое состояние браузера. Так один и тот же
«сайт+аккаунт» навсегда получает один и тот же `bp_...`, и повторные логины его просто
обновляют, а не плодят новые.

**Это работает только у логин-бота.** У парсер-бота `persist_browser_session` должен быть
**выключен** — иначе он либо копит собственный (общий на всех поставщиков!) профиль, либо
пытается писать в чужой. Подробности в §8.4.

### 3.3 Явная передача профиля побеждает всё

При запуске **любого** воркфлоу можно передать в теле запроса `browser_profile_id` —
конкретный id профиля, который нужно загрузить в браузер этого run'а. Это работает даже
если запускаемый воркфлоу профилем не владеет (не он его создавал) — он получит его как
"foreign profile": стартует с его куками, но по завершении **не запишет** в него ничего
нового (`_resolve_picked_profile_role` → `foreign_auto`,
`skyvern/forge/sdk/workflow/service.py:2145`).

Это ровно то, что нужно: логин-бот **владеет и обновляет** профиль, парсер-бот **читает**
его read-only. Свежесть сессии поддерживает только логин-бот, парсер её не портит и не
протухает досрочно.

### 3.4 Browser Session — тот же браузер, а не слепок

Профиль — это снятый снимок *после* закрытия браузера. Browser Session (`pbs_...`) — это
**сам процесс браузера**, который Skyvern держит живым между запусками. Можно запустить
воркфлоу А с `browser_session_id=X`, он что-то сделает в этом браузере, завершится (браузер
**не закрывается**), затем запустить воркфлоу Б с тем же `browser_session_id=X` — он
продолжит работу в том же самом браузере: те же куки в памяти, тот же исходящий IP, тот же
browser fingerprint, живой `sessionStorage`.

Это строже профиля: профиль переносит куки/localStorage, но не sessionStorage и не привязку
к IP. Часть порталов проверяет IP при каждом запросе или хранит токен только в
sessionStorage — для них профиль не работает в принципе, а сессия работает всегда (см. §7).

Session умирает сама по таймауту (`timeout` в минутах при создании; активность продлевает
жизнь до `idle`-предела, но есть жёсткий потолок 24 часа —
`skyvern/schemas/browser_session_timeouts.py`). Никто не обязан её закрывать явно.

## 4. Аутентификация и общий формат запросов к Skyvern API

Все запросы — обычный HTTPS + JSON. Авторизация — заголовок:

```
x-api-key: <ваш Skyvern API-ключ>
```

(`skyvern/forge/sdk/services/org_auth_service.py:389` — ключ это JWT, из которого сервер
достаёт `organization_id`; **ключ привязан к конкретному серверу/базе**, при переезде на
другой Skyvern-инстанс старый ключ не подойдёт даже если формально расшифровывается — см.
§8.3, это реальный баг, на который мы наступили).

**Важно про базовый URL**: у Skyvern два роутера с разными префиксами на одном хосте
(`skyvern/forge/api_app.py:400-402`):

- `/api/v1/...` — запуск и статус воркфлоу (`legacy_base_router`)
- `/v1/...` — Browser Sessions API и часть более новых эндпоинтов (`base_router`)

Это не опечатка и не альяс — реально два разных префикса. Перепутать легко (мы наступили и
на это), и сервер в ответ честно отдаёт `404 Not Found`, не намекая на причину.

## 5. Запуск воркфлоу (диспатч) — точка входа №1

### Запрос

```
POST {apiBaseUrl}/api/v1/workflows/{workflow_id}/run
x-api-key: <ключ>
Content-Type: application/json
```

Тело для **логин-бота**:

```json
{
  "data": {
    "website_url": "https://portal.dida.com/login",
    "bitwarden_item_id_input": "d5fd3424-420a-454d-a2fb-b28900b7f112",
    "agent_code": ""
  },
  "webhook_callback_url": "https://ваш-оркестратор.example.com/callback/abc123",
  "browser_session_id": "pbs_562727332591518724"
}
```

`data` — это набор **параметров воркфлоу** (тех самых, что определены в его
`workflow_definition.parameters` — см. приложенные ранее JSON логин- и парсер-ботов). Ключи
внутри `data` обязаны совпадать с именами параметров конкретного воркфлоу; для другого
поставщика/бота набор ключей может быть другим — это не общий контракт Skyvern, а контракт
конкретного вашего воркфлоу.

`browser_session_id` — опционально, только если фид работает в режиме «живая сессия»
(§7). Если его не передавать, а вместо этого передать `browser_profile_id` — вот так:

Тело для **парсер-бота** (профильный режим):

```json
{
  "data": {
    "website_url": "https://portal.dida.com/login",
    "booking_id": "18243414088"
  },
  "webhook_callback_url": "https://ваш-оркестратор.example.com/callback/abc123",
  "browser_profile_id": "bp_561991113966861882"
}
```

`browser_profile_id` и `browser_session_id` — взаимоисключающие способы посадить run на
готовое браузерное состояние; можно не передавать ни то ни другое (тогда воркфлоу стартует
согласно своим собственным настройкам — своему managed-профилю, если он есть, или с чистого
листа).

`webhook_callback_url` — см. §6.2. Можно не передавать вовсе и просто опрашивать статус
(§6.1) — оба способа поддерживаются одновременно.

### Ответ (сразу, синхронно)

```json
{
  "workflow_id": "wpid_561235100938517884",
  "workflow_run_id": "wr_564214417125408454",
  "status": "created"
}
```

(поле `workflow_id` в ответе — это ровно тот id, который вы передали в URL; в некоторых
версиях API он дублируется под алиасом `agent_id`). Дальше вам нужен только
`workflow_run_id` — это ключ ко всем последующим запросам про этот конкретный прогон.

**Никакой другой информации в этом ответе нет** — run только что создан, он ещё не начал
выполняться. Даже если передали профиль/сессию — узнать, подошли они или нет, можно только
из статуса (см. §6).

## 6. Ожидание результата — точка входа №2

Skyvern поддерживает два независимых способа узнать, что прогон закончился. Их можно
комбинировать (мы используем оба: колбэк — быстрый путь, поллинг статуса — на случай, если
колбэк потерялся).

### 6.1 Активный опрос (poll)

```
GET {apiBaseUrl}/api/v1/workflows/{workflow_id}/runs/{workflow_run_id}
x-api-key: <ключ>
```

Ответ, например, во время выполнения:

**Поля, которые реально нужны оркестратору** (остальные — для UI/дебага):

| поле | что означает | где смотреть в коде |
|---|---|---|
| `status` | см. таблицу статусов ниже | `skyvern/forge/sdk/workflow/models/workflow.py:223` |
| `outputs.extracted_information` | **всегда список** (даже если один блок извлечения) — берите `[0]`, если он единственный. Пусто/нет ключа, пока run не `completed` | `service.py:8290-8300` — агрегируется из всех extraction-блоков воркфлоу |
| `failure_reason` | человекочитаемая причина неудачи (для логин-бота — почему не смог войти; для парсер-бота — почему не нашёл booking) | заполняется агентом |
| `browser_profile_id` | профиль, с которым **стартовал** этот run (сид) | — |
| `browser_sink_profile_id` | профиль, в который run **записал** новое состояние по завершении. **На первом-в-жизни логине по новому ключу может быть заполнено только это поле**, а `browser_profile_id` останется `null` — обязательно берите `browser_sink_profile_id ?? browser_profile_id`, иначе на первом логине потеряете id только что созданного профиля | `service.py:2088-2111` (`_resolve_run_seed`, комментарий "Own memory exists but has no content yet") |
| `browser_session_id` | если run создавался/шёл с явной browser session — её id тут | — |

**Статусы (`status`)** — полный список, финальные помечены:

| статус | финальный? | смысл |
|---|---|---|
| `created` | нет | run принят, ещё не начал исполняться |
| `queued` | нет | ждёт свободного воркера |
| `running` | нет | выполняется |
| `paused` | нет | приостановлен (человеческое вмешательство и т.п. — в нашем сценарии не встречается) |
| `completed` | **да** | успех |
| `failed` | **да** | агент не смог выполнить задачу (см. `failure_reason`) |
| `terminated` | **да** | принудительно остановлен |
| `canceled` | **да** | отменён |
| `timed_out` | **да** | **это статус самого Skyvern**, run превысил свой внутренний лимит времени. **Не путать** с «оркестратор не дождался ответа» — это другое понятие, см. ниже |

(`skyvern/forge/sdk/workflow/models/workflow.py:223-241`, `is_final()`)

Опрашивать нужно **до тех пор, пока статус не станет одним из пяти финальных**. Мы
опрашиваем раз в 5 минут (см. §6.3 почему именно так) с общим потолком ожидания — если
за, скажем, 30 минут run так и не финализировался, оркестратор сам считает его
«таймаутом ожидания» (это n8n-/оркестраторский таймаут, не `timed_out` от Skyvern —
два разных, не путать в диагностике и логах!).

### 6.2 Вебхук-колбэк (push)

При запуске можно передать `webhook_callback_url` — HTTP-адрес, куда Skyvern сам сделает
`POST` **ровно один раз**, когда run дойдёт до финального статуса (успех или любая
неудача) — `execute_workflow_webhook` вызывается из cleanup-пути прогона
(`service.py:8864`).

**Доставка с ретраями, но короткими**: до 3 попыток с интервалом порядка секунды, и
**неретраится** на некоторых кодах (в т.ч. на 404) —
`skyvern/services/webhook_delivery.py:29-52`. Если ваш эндпоинт был недоступен дольше
пары секунд (перезапуск, деплой, сетевой сбой) — колбэк **потерян навсегда**, повторной
попытки через минуту/час не будет. **Проектируйте систему так, будто колбэк может не
прийти вообще** — обязательно имейте резервный поллинг (§6.3), не полагайтесь только на
push.

**Запрос, который вы получите:**

```
POST <ваш webhook_callback_url>
Content-Type: application/json
x-skyvern-timestamp: 1755523200
x-skyvern-signature: 3f9a1c...  (hex, HMAC-SHA256)
```

Тело — большой JSON, объединение статуса run'а (все поля из §6.1) и доп. метаданных запуска
(`prepare_workflow_webhook`, `service.py:8882`). Практически важные поля — те же, что в
§6.1 (`status`, `outputs.extracted_information`, `failure_reason`, `browser_profile_id`,
`browser_sink_profile_id`), плюс:

```json
{
  "run_id": "wr_564214417125408454",
  "run_type": "workflow_run",
  "status": "completed",
  "app_url": "https://skyvern.dev.srv.team/runs/wr_564214417125408454",
  "output": { "...": "то же, что outputs.extracted_information[0] обычно" },
  "...": "и остальные поля из GET .../runs/{id}"
}
```

**Верификация подлинности (рекомендую сделать, если колбэк принимает публичный эндпоинт)**:
подпись — это `HMAC-SHA256(key=ваш_api_key, message=raw_json_body)` в hex
(`skyvern/forge/sdk/core/security.py:48-61`). Пересчитайте её на своей стороне над **сырым**
телом запроса (до парсинга JSON — из-за форматирования строка может не совпасть после
`JSON.parse` → `JSON.stringify`) и сравните с заголовком `x-skyvern-signature`.

**Важный архитектурный урок, который мы получили на практике** — если ваш колбэк-эндпоинт
не привязан жёстко к конкретному run'у (например, общий URL на весь процесс/очередь, как
`$execution.resumeUrl` в n8n), то *любой* колбэк — включая колбэк от предыдущей, уже
обработанной задачи — разбудит ожидающего, и вы примете чужой ответ за свой. **Каждый
диспетчер задачи должен ждать колбэк на уникальном, ей одной принадлежащем адресе/токене**
(например, `POST /callback/{job_uuid}` с job_uuid, сгенерированным перед диспатчем), либо —
если общий URL неизбежен — при пробуждении **обязательно перепроверять реальный статус**
через GET (§6.1), а не доверять самому факту пробуждения. Мы наступили ровно на это:
общий webhook-URL + доверие факту колбэка без проверки статуса → колбэк от run'а N будил
ожидание run'а N+1, N+1 ещё выполнялся → ложный «таймаут» → диспатч N+2 → колбэк N+1
будил уже его — цепочка сдвинутых состояний на всю оставшуюся очередь. Лечится тем, что
пробуждение (по колбэку ИЛИ по локальному таймеру опроса) всегда трактуется только как
«повод проверить статус GET'ом», а не как «run точно закончился».

### 6.3 Наша итоговая стратегия ожидания

Гибрид: подписываемся на колбэк (быстрый путь — большинство run'ов завершаются за 2-5 мин,
узнаём почти мгновенно), но параллельно держим локальный таймер на 5 минут; если он
срабатывает раньше колбэка — сами делаем GET статуса. По любому пробуждению (колбэк или
таймер) **всегда** делаем GET и смотрим реальный `status`:
- финальный → обрабатываем результат;
- нефинальный, но общий бюджет времени на этот run ещё не исчерпан (у нас: 30 минут для
  парсера, 15 минут для логина, настраивается) → снова ставим таймер на 5 минут и ждём;
- нефинальный и бюджет исчерпан → считаем задачу «таймаутом ожидания» (это наш собственный
  статус, не путать с `status=timed_out` от Skyvern — тот тоже возможен и это тоже
  финальный статус, просто из другой категории причин).

## 7. Browser Sessions API — точка входа №3 (для «упрямых» порталов)

Используется только для фидов с `use_browser_session=TRUE` — когда портал не принимает
перенесённый профиль (проверяет исходящий IP, держит токен в `sessionStorage`, слишком
чувствителен к browser fingerprint).

### Создать сессию

```
POST {apiBaseUrl}/v1/browser_sessions      <-- ВНИМАНИЕ: префикс /v1, НЕ /api/v1
x-api-key: <ключ>
Content-Type: application/json

{ "timeout": 120 }
```

`timeout` — минуты жизни по умолчанию (диапазон 5–1440 минут = 24 часа —
`skyvern/schemas/browser_session_timeouts.py`). Реальная активность (любая CDP-команда
внутри run'а, использующего эту сессию) продлевает жизнь до отдельного idle-предела, но
общий жёсткий потолок — 24 часа с момента создания, преодолеть его нельзя.

Ответ:

```json
{
  "browser_session_id": "pbs_562727332591518724",
  "organization_id": "org_...",
  "status": "created"
}
```

### Проверить, жива ли сессия

```
GET {apiBaseUrl}/v1/browser_sessions/{browser_session_id}
x-api-key: <ключ>
```

- Сессия существует и активна → `200` с телом, где `status` не финальный
  (`completed`/`failed`/`timeout`/`terminated`/`closed`) и `completed_at` пусто.
- Сессия истекла/закрыта или id вообще не существует (опечатка, чужая организация, давно
  удалена) → либо `404`, либо `200` с финальным `status`/заполненным `completed_at` —
  **проверяйте оба варианта**, не полагайтесь только на HTTP-код.

### Использование

Просто передайте `browser_session_id` в теле запуска **любого** воркфлоу (§5) вместо
`browser_profile_id` — этот run подключится к уже работающему браузеру этой сессии.
**Явного «закрыть сессию» вызова можно не делать вовсе** — она умрёт сама по таймауту; но
если хотите закрыть раньше (сессия больше не нужна) — `POST
{apiBaseUrl}/v1/browser_sessions/{id}/close`.

### Логика оркестратора для session-фида (зеркало логики профиля из §8.2)

1. В `Feeds.browser_session_id` есть значение → `GET .../browser_sessions/{id}`.
   Жива → диспатчим парсер **сразу** с этим `browser_session_id`, без логина (браузер уже
   залогинен предыдущей задачей этого фида).
2. Сессии нет или она мертва → создаём новую → логиним в ней (`Dispatch Login` с этим
   `browser_session_id`) → парсим в ней же → новый `pbs_...` записываем в `Feeds`.
3. Парсер упал на переиспользуемой сессии (браузер жив, но токен внутри портала протух) →
   один повторный логин **в той же сессии**, один повторный парсинг — точно та же
   семантика восстановления, что и для профиля (§8.3).

## 8. Полная логика оркестратора на один booking_id (state machine)

Псевдокод, независимый от инструмента:

```
для каждой строки Jobs со status != "completed":
    feed  = найти в Feeds по feed_id                     # см. 8.1, ошибка -> status=error
    supplier = найти в Suppliers по feed.website_url      # см. 8.1, ошибка -> status=error
    пометить Jobs.status = "processing"

    если feed.use_browser_session == true:
        сессия = проверить feed.browser_session_id (GET .../browser_sessions/{id})
        если сессия жива:
            attempt = { browser_session_id: сессия.id, allow_recovery: true, login_ran: false }
            перейти сразу к ЭТАП «парсинг»
        иначе:
            перейти к ЭТАП «логин» с browser_session_id = null (создать новую сессию)
    иначе:
        если feed.browser_profile_id пуст:
            перейти к ЭТАП «логин» (без сессии, будет создан/найден профиль)
        иначе:
            attempt = { profile_id: feed.browser_profile_id, allow_recovery: true, login_ran: false }
            перейти сразу к ЭТАП «парсинг»

    ЭТАП «логин»:
        если use_browser_session и browser_session_id пуст:
            browser_session_id = POST .../browser_sessions { timeout }         # создать
        POST .../workflows/{login_workflow_id}/run
            data = { website_url, bitwarden_item_id_input, agent_code }
            browser_session_id = <если есть>
        дождаться финального статуса (§6)
        если login.status != "completed":
            Jobs.status = "failed"; recovered_via_login = "<профиль/сессия> — login failed/timeout"
            ЗАПИСАТЬ И ВЫЙТИ (парсер вообще не запускаем — бессмысленно)
        иначе:
            new_id = login.browser_sink_profile_id ?? login.browser_profile_id   # для профильного режима
                     ИЛИ browser_session_id                                       # для session-режима
            Feeds[feed_id].browser_profile_id / browser_session_id = new_id      # запомнить на будущее
            attempt = { profile_id или browser_session_id: new_id,
                        allow_recovery: false,     # <-- второй логин подряд не допускаем, см. ниже
                        login_ran: true }

    ЭТАП «парсинг»:
        POST .../workflows/{parser_workflow_id}/run
            data = { website_url, booking_id }
            browser_session_id = attempt.browser_session_id  <- если есть, иначе
            browser_profile_id = attempt.profile_id           <- если есть (сессия и профиль не передаются одновременно)
        дождаться финального статуса (§6)

        если parser.status == "completed":
            Jobs.status = "completed"; extracted_data = parser.outputs.extracted_information[0]
            ЗАПИСАТЬ И ВЫЙТИ

        если parser.status == "timed_out" (или наш таймаут ожидания):
            Jobs.status = "timeout"
            ЗАПИСАТЬ И ВЫЙТИ    # восстановление НЕ пробуем — если сайт завис, повторный логин не поможет

        # parser.status в {"failed","terminated","canceled"}:
        если attempt.allow_recovery == true:
            вернуться к ЭТАП «логин» (это тот самый единственный повторный логин)
        иначе:
            Jobs.status = "failed"
            ЗАПИСАТЬ И ВЫЙТИ
```

### 8.1 Инфраструктурные ошибки — отдельная ветка, не смешивать со `failed`

`Jobs.status = "error"` — это отдельная категория от `"failed"`. `"failed"` значит «агент
честно попробовал и не смог» (полезный сигнал: возможно, реальная проблема на сайте
поставщика). `"error"` значит «сама попытка не состоялась» — не найден `feed_id`/связка с
Suppliers, Skyvern вернул HTTP-ошибку на сам диспатч (неверный `workflow_id`, сеть, авторизация
и т.п.). При разборе инцидентов в первую очередь смотрите `error` — это обычно
конфигурационная проблема оркестратора, а не проблема сайта поставщика.

### 8.2 Почему проверка `browser_profile_id`/`browser_session_id` должна читать таблицу заново на каждой задаче

Если у фида несколько задач в одной пачке (например 5 booking_id одного поставщика), и на
старте пачки профиля ещё не было — первая задача залогинится и запишет `bp_...` в таблицу.
**Вторая задача того же фида должна увидеть уже этот только что записанный `bp_...`**, а не
работать по снимку таблицы, сделанному в начале всей пачки. Если ваш инструмент кеширует
таблицу целиком в памяти на старте (как это изначально было сделано и оказалось багом) —
каждая задача фида будет логиниться заново, теряя всю экономику §1. Решение — либо не
кешировать вовсе (читать актуальную строку прямо перед принятием решения), либо кешировать,
но **инвалидировать/обновлять запись в кеше** сразу после успешного логина.

### 8.3 Почему допускается ровно ОДНА попытка восстановления, не больше

`allow_recovery` выставляется в `false` сразу после того, как решение «логиниться» уже было
принято один раз в рамках обработки этой задачи. Если бы это ограничение отсутствовало и
парсер продолжал падать (например, сайт поставщика реально лежит, а не сессия протухла),
оркестратор зациклился бы: логин → парсинг → падение → логин → ... до истечения общего
лимита времени, тратя деньги на LLM-вызовы логин-бота без всякого смысла. Одна попытка
восстановления — разумный компромисс: покрывает 100% случая «сессия протухла», не даёт
зациклиться на случае «сайт лёг».

### 8.4 Почему у парсер-бота ОБЯЗАТЕЛЬНО выключен `persist_browser_session`

Если у парсер-воркфлоу включён Save & Reuse Session, но **не задан** `browser_profile_key`
(а ему это поле и не нужно — профилями управляет логин-бот), Skyvern трактует это как «нет
пикового профиля → копи один свой» (`_resolve_run_seed`, ветка «No pick + Save ON»,
`service.py:2078-2111`): в результате у парсер-воркфлоу заводится **один общий**
managed-профиль на **все** его запуски, для всех поставщиков и фидов разом. Любой запуск
парсера, куда явный `browser_profile_id`/`browser_session_id` по какой-то причине не долетел
(баг оркестратора, гонка, пустая ячейка), сидируется куками **того поставщика, который
парсился последним** — тихая перекрёстная контаминация сессий между поставщиками, которую
очень трудно диагностировать постфактум (симптом: браузер парсера открывается на «странном»
чужом сайте вместо ожидаемого). Правило простое: у бота, который сам логинится и должен
помнить сессию (логин-бот) — Save & Reuse включён + задан ключ. У бота, который только
читает переданный ему профиль (парсер-бот) — Save & Reuse **выключен полностью**.

## 9. Сквозной пример: полный путь одного booking_id

Фид `DDA.B2C_CUG_DIRECT`, в `Feeds.browser_profile_id` пусто (первый прогон).

**1.** Оркестратор находит строку Jobs `{feed_id: "DDA.B2C_CUG_DIRECT", booking_id:
"18243414088", status: ""}`, помечает `status=processing`.

**2.** Резолвит через Feeds → Suppliers: `website_url=https://portal.dida.com/login`,
`login_workflow_id=wpid_561706314685463142`, `parser_workflow_id=wpid_561235100938517884`.

**3.** `browser_profile_id` пуст → сразу логин:

```
POST https://skyvern-api.dev.srv.team/api/v1/workflows/wpid_561706314685463142/run
{
  "data": {
    "website_url": "https://portal.dida.com/login",
    "bitwarden_item_id_input": "d5fd3424-420a-454d-a2fb-b28900b7f112",
    "agent_code": ""
  },
  "webhook_callback_url": "https://orchestrator.example.com/callback/job-18243414088-attempt-1"
}
→ 200 { "workflow_run_id": "wr_564213232362144942", "status": "created" }
```

**4.** Ждём (колбэк или поллинг). Финальный опрос:

```
GET .../workflows/wpid_561706314685463142/runs/wr_564213232362144942
→ { "status": "completed", "browser_profile_id": null,
    "browser_sink_profile_id": "bp_561991113966861882", ... }
```

**5.** `status=completed` → берём `new_id = "bp_561991113966861882"` (из
`browser_sink_profile_id`, т.к. `browser_profile_id` пуст — это первый логин по этому
ключу). Пишем в `Feeds`: `browser_profile_id=bp_561991113966861882`,
`last_login_status=completed`.

**6.** Парсим:

```
POST .../workflows/wpid_561235100938517884/run
{
  "data": { "website_url": "https://portal.dida.com/login", "booking_id": "18243414088" },
  "browser_profile_id": "bp_561991113966861882",
  "webhook_callback_url": "https://orchestrator.example.com/callback/job-18243414088-attempt-1"
}
→ 200 { "workflow_run_id": "wr_564210913079804394", "status": "created" }
```

**7.** Финальный статус:

```json
{
  "status": "completed",
  "outputs": {
    "extracted_information": [{
      "hotelName": "Ibis Almaty Jetisu", "address": "Abylai Khan Avenue 5",
      "checkinDate": "2026-08-15", "checkoutDate": "2026-08-16",
      "adultCount": 1, "guestNames": ["CEYHUN HASANOV"], "hcn": "18243414088"
    }]
  }
}
```

**8.** Пишем в Jobs: `status=completed`, `workflow_run_id=wr_564210913079804394`,
`recovered_via_login="not needed"`, `extracted_data=<весь JSON выше>`, плюс отдельные
колонки `hotelName`, `checkinDate` и т.д. — тем же JSON'ом, просто разложенным.

**Следующая задача того же фида** (`booking_id="183110892049"`) на этой же итерации пачки:
на шаге 3 `Feeds.browser_profile_id` уже равен `bp_561991113966861882` (мы его только что
записали) → идём сразу в парсинг, логин пропускаем.

**Пример с восстановлением.** Позже, через несколько часов, третья задача того же фида:
профиль в таблице есть, идём сразу в парсинг → Skyvern возвращает `status=failed`,
`failure_reason="No matching booking found — login page detected"` (сессия протухла и
парсер уткнулся в форму логина). `allow_recovery=true` (это первая попытка в рамках этой
задачи) → логинимся заново по тому же ключу → Skyvern **находит существующий**
`bp_561991113966861882` (тот же ключ `website_url + bitwarden_item_id_input` дал тот же
хеш) и обновляет его → парсим второй раз, уже с обновлённым профилем → `completed`. В Jobs
это отражается как `recovered_via_login="profile expired — logged in, parser succeeded"`.

## 10. Итоговый чеклист для реализации на новом стеке

1. **Хранилище** трёх сущностей (Suppliers, Feeds, Jobs) — таблицы, коллекции, что угодно
   с возможностью читать «свежую» строку Feeds непосредственно перед принятием решения
   (не кешировать статично на весь батч, см. §8.2).
2. **HTTP-клиент** с заголовком `x-api-key`, знающий про два префикса (`/api/v1` для
   workflows, `/v1` для browser_sessions).
3. **Диспатч** воркфлоу: `POST /api/v1/workflows/{id}/run`, тело `{data, webhook_callback_url?,
   browser_profile_id? | browser_session_id?}`.
4. **Ожидание с перепроверкой**: любое пробуждение (колбэк ИЛИ локальный таймер) → `GET
   .../runs/{run_id}` → решение только по реальному `status` оттуда, никогда по самому
   факту получения колбэка. Общий дедлайн ожидания на уровне задачи, не только на уровне
   одного цикла опроса.
5. **Коалесинг id профиля**: `browser_sink_profile_id ?? browser_profile_id`.
6. **State machine на задачу**: пусто→логин→парсинг; профиль-есть→сразу-парсинг;
   failed(не timeout)+не восстанавливались ещё→логин→парсинг ещё раз; timeout→сразу
   финал без восстановления; ровно один заход на восстановление на задачу.
7. **Различать три категории неуспеха** в статусе задачи: `failed` (агент не справился),
   `timeout` (не дождались финализации), `error` (сама попытка не состоялась —
   конфигурация/сеть/авторизация).
8. **У парсер-воркфлоу в Skyvern выключить Save & Reuse Session.** У логин-воркфлоу —
   включить и задать `browser_profile_key` по шаблону вида
   `{{website_url}}-{{bitwarden_item_id_input}}`, чтобы один сайт+аккаунт стабильно давал
   один и тот же профиль.
9. Для порталов, которые не принимают перенесённые профили — Browser Sessions API вместо
   профиля (§7), с той же логикой «жива → используем как есть, мертва → логин заново»,
   зеркально §8.2–8.3.

Готовые примеры реальных запросов/тел выше (§5, §6, §7, §9) можно использовать напрямую как
тест-кейсы при разработке нового оркестратора — прогнать их curl'ом руками до того, как
писать код, чтобы увидеть форматы вживую на вашем сервере.
